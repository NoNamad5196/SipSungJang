# V2 공통 도메인과 데이터 보존

## 식별자 계약

| 도메인      | 기준 식별자                               | 현재 저장/제공 위치                      |
| ----------- | ----------------------------------------- | ---------------------------------------- |
| User        | Firebase Auth UID                         | 인증 세션의 `userId`                     |
| GameMaster  | `genshin-impact` 같은 고정 ID             | `src/lib/catalog.ts`, `GET /api/catalog` |
| Franchise   | `honkai` 같은 고정 ID                     | 동일 카탈로그                            |
| UserGame    | 개인 수첩 항목 ID + `user_id` + `game_id` | `users/{uid}/games/{entryId}`            |
| UserProfile | UID                                       | `users/{uid}.profile`                    |
| Character   | 캐릭터 문서 ID                            | `users/{uid}/characters/{id}`            |

**`Game.id`와 `Game.game_id`는 다른 개념입니다.** 기존 타입 이름 `Game`은 호환성을 위해 UserGame에 SipSungJang의 퀘스트·목표·파티를 합친 저장 문서입니다. 공통 게임 자체는 `GameMaster`입니다. `toSharedUserGame()`은 육성 필드를 제외한 공통 부분을 추출합니다.

기존 캐릭터의 `game_id`는 역사적으로 **개인 수첩 항목 ID**를 참조합니다. 전역 GameMaster ID로 해석하거나 기존 문서 ID를 일괄 변경하지 않습니다. 캐릭터에서 전역 게임으로 이동하려면 연결된 UserGame의 `game_id`를 읽습니다.

```text
GameMaster(genshin-impact)
  ├─ SipSungJang: UserGame.game_id → 퀘스트·육성·파티
  ├─ OtakuHub: event.game_id → 이벤트·일정 (후속 연동)
  └─ GachaGuard: spending.game_id → 소비·예산 (후속 연동)
```

## 중복 방지와 확장

한글/영문 별칭, 공백, 대소문자, 일부 구두점을 정규화해 카탈로그에서 먼저 조회합니다. 모르는 게임은 정규화한 이름의 UTF-8 hex로 `custom-...` ID를 만듭니다. 게임 표시 이름을 수정해도 기존 공통 ID는 유지합니다. 클라우드 신규 등록·백업 복원은 공통 ID를 문서 ID로 사용하고 트랜잭션으로 중복 쓰기를 차단합니다. V1의 무작위 개인 ID는 그대로 둡니다.

카탈로그 API는 버전 1의 `{version, games, franchises}` JSON을 제공하며 개인정보·개인 수첩을 노출하지 않습니다. 다른 프런트엔드는 이 API에서 동일한 ID를 읽고 선택해야 합니다. 카탈로그 미등록 게임의 서로 다른 별칭까지 자동 판별하지는 않으므로, 정식 카탈로그 편입 시 별칭/기존 custom ID의 명시적 연결표가 필요합니다. 기존 ID를 임의로 바꾸지 않습니다.

별도 패키지·마이크로서비스·모노레포는 도입하지 않습니다. 공통 계정을 연결할 때는 세 사이트가 동일 Firebase 프로젝트의 UID를 사용해야 합니다. 별개 Firebase 프로젝트의 UID나 이메일을 단순히 같은 사용자로 간주하지 않습니다. 서로 다른 출처의 로그인 세션 공유는 런처 링크만으로 완성되지 않으며 후속 인증 연동 작업입니다.

## V1 읽기와 V2 저장

- 기존 Firestore 경로, 사용자 UID, 개인 게임·캐릭터 ID, 일반/파티 메모를 유지합니다.
- 구 `weekly_tasks`/`weekly_tasks_done`을 안정적인 ID의 퀘스트로 읽습니다. V2 저장 시 두 배열도 동기화해 기존 백업과의 의미를 유지합니다. 새 `quests`가 있으면 이를 우선합니다.
- 읽기 시 기본값을 채우지만 전체 DB에 마이그레이션 쓰기를 실행하지 않습니다. 사용자가 수정한 문서만 병합 저장합니다.
- 클라우드 게임/캐릭터 삭제는 `deleted_at`으로 보관합니다. 삭제된 게임에 연결된 캐릭터는 숨깁니다. 동일한 결정적 ID의 게임을 다시 등록하면 보관 기록을 복원합니다.
- 기기 저장은 단일 `sipsungjang_v2` JSON, 예시는 `sipsungjang_demo_v2` JSON입니다. V1 로컬 키 `sipsungjang_games`/`sipsungjang_characters`는 삭제하지 않습니다. 원본 읽기 실패 시 빈 데이터로 덮어쓰지 않습니다.
- 기기 변경 전 직전 JSON을 `_recovery` 키에 보관합니다. 저장 용량 오류는 저장 성공으로 표시하지 않습니다. 삭제 전 전체 백업을 권장하며, 복구 원본 다운로드는 설정에서 가능합니다.

## 백업 병합 정책

파일은 V1 또는 V2, 최대 10MB입니다. 버전/배열/식별자/중복 ID/캐릭터 참조를 검사한 뒤 가져올 개수를 보여줍니다. 동일한 공통 게임 ID와 해당 게임의 동일 이름 캐릭터는 기존 기록을 우선합니다. 이미 존재하는 게임의 퀘스트·파티와 현재 프로필은 덮어쓰지 않습니다. 새로운 캐릭터의 게임 참조 및 새 게임의 파티 슬롯은 병합 결과에 맞게 바꿉니다.

클라우드 가져오기는 한 번에 신규 게임+캐릭터 450개까지 원자적 트랜잭션으로 추가합니다. 충돌하는 문서는 덮어쓰지 않고 재확인을 요청합니다. 백업 전체 교체나 자동 클라우드/기기 동기화는 제공하지 않습니다.

## 시간과 집계

날짜·갱신 계산은 한국 표준시 기준입니다. 갱신 예정 시각과 안내는 프로필에 따라 계산합니다. 주간 완료율은 현재 수첩에 저장된 모든 퀘스트의 완료 개수 기준입니다. 예상 플레이량은 휴식/방치 상태를 제외합니다. 자동 날짜 초기화로 사용자의 기록을 지우지 않으며 게임 상세의 다시 시작 버튼으로 일일·주간 진행도를 명시적으로 초기화합니다. 이벤트 진행도는 유지됩니다.
